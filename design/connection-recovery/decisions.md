# Decisions

## Open questions

- O-1 Error names. Settled: calls during recovery raise a recovering error whose bases D-30 sets, and lost confirmations get an outcome-unknown notification (D-4). Open: the names.
- O-2 A "reconnected, replaying" signal. Settled: `RECOVERING -> OPEN` comes after replay (D-7). Open: whether to tell the application when the socket is back and replay starts, as Java's `handleTopologyRecoveryStarted` does.
- O-6 A re-subscribed consumer. Settled: the cancel callback fires when a consumer is given up (D-6). Open: whether the application hears anything when the broker cancels a consumer and re-subscription succeeds.
- O-7 An opt-in queue-and-retry mode. Settled: fail-fast is the default (D-11). Open: a follow-on mode that holds a call for a bounded time and retries it. It must say what a held `basic_publish` returns as its sequence number, whether an RPC whose caller waits for a result can be held without blocking, and how held calls stay ordered with calls made after recovery.
- O-8 Replacing replay. Settled: the delay policy and the filter are pluggable (D-2, D-8). Open: whether an application may replace topology replay, as Go's `TopologyRecovery` interface allows, which would make the record's types public API.
- O-9 Credentials on reconnect. Settled: the default policy retries a connection forever (D-2). Open: refreshing a token, such as OAuth 2, before each attempt, without which an expired token is retried forever.
- O-10 Deterministic test timing. Settled: SC-2, SC-3, SC-12, SC-15, SC-22, SC-23, SC-25, SC-33, SC-34 and SC-39 need a fault at a chosen step. Open: whether a test-only hook may hold a connection attempt or pause replay to provide it.
- O-11 Broker versions in CI. Settled: the scenarios need 4.1 or 4.2, one of 4.3.0 to 4.3.6, and 4.3.7 or later. Open: which versions phase 1 pins and how, and how many consecutive passing runs count as stable.
- O-12 Identifying an unwritten publish. Settled: in confirm mode, a publish accepted but not yet written at the drop is reported as outcome unknown (D-28). Open: how the notification identifies it, given it has no sequence number yet.
- O-13 The default jitter. Settled: the default delay doubles from 1 second to 30 (D-2). Open: the jitter's form and range.
- O-14 Listener reasons. Settled: every transition carries a reason (I-9). Open: its type, what `RECOVERING -> OPEN` carries besides the skipped entities, and which reason `CLOSED` carries after a `close()` during recovery.
- O-17 The driver's ordering. Settled: one driver runs every recovery (D-10), and a connection recovery takes over channel recoveries in progress. Open: whether a broker-cancelled consumer's first re-subscription waits for the delay, whether one channel's delay holds back other channels and broker-cancel re-subscriptions, how a connection drop interrupts a channel recovery's delay or a blocking call, and whether an absorbed channel's attempt count carries over.
- O-18 Retrying a held resource. Settled: a step refused because the old connection holds a resource is retried through the delay policy (D-24). Open: how pika tells that refusal from a revoked permission, since both can be 403 (AMQP 1.0 matches the error text); which resource the policy is told about; its default limit; and whether the step is then skipped and reported (D-8) or its consumer reported through the cancel callback.
- O-19 Skipping a refused step. Settled: a step that fails for good is skipped and replay continues (D-8). Open: since the refusal closes the channel, whether that channel's settings and already re-subscribed consumers are redone, which channel replays entities declared on a channel since closed, and whether the skipped entity stays recorded for the next recovery.
- O-20 Topology recovery off. Settled: consumers are not re-subscribed after connection recovery (D-8), and channel recovery restores only settings. Open: whether a broker-cancelled consumer is still re-subscribed, and whether the application hears that its consumers have stopped.
- O-21 The outcome-unknown notification's shape. Settled: it is separate from the confirm callback and names the affected sequence numbers (D-4). Open: one notification per publish or one per lost channel.
- O-22 How long a channel must stay open. Settled: a channel's attempt count resets only once it has stayed `OPEN` for a while after recovering (D-34). Open: how long.
- O-23 A `multiple` acknowledgement past a cancelled consumer's tags. Settled: single acknowledgements of a cancelled consumer's tags are dropped. Open, to be investigated: how a `multiple` acknowledgement that reaches past a cancelled consumer's tags is handled, given that on the same channel it also covers other consumers' live deliveries.

## Settled

Each states the decision, its reason, then how Java (AMQP 0.9.1), the AMQP 1.0 Java client, .NET and Go compare where they were checked. `concepts.md` has the full behaviour.

- D-1 Recovery is on by default and can be turned off. Applications should not need recovery code to survive a broker restart. Java, AMQP 1.0 and .NET are on by default; Go is off.
- D-2 One delay policy decides every retry, told the attempt number, the last error, and which connection, channel or consumer is recovering. An application can then stop on the errors it considers permanent. A connection's count starts again after each success, and a channel's as D-34 sets. The defaults, and when the delay applies, are in `concepts.md`. The connection waits before its first attempt, as all four clients do; a channel's first reopen ignores the delay, as Go's does. The default backs off exponentially rather than at Java's fixed 5 seconds, so clients reconnecting to a broker that is coming back do not all retry at the same pace. Java and AMQP 1.0 retry the connection at a fixed 5 seconds and give that policy only the attempt number, though Java's opt-in topology retry handler and Go's `OnTopologyEntityError` hook see each entity and its error, and AMQP 1.0 retries only errors its recovery rule accepts. .NET retries forever at 5 seconds with no policy; Go stops after 5 attempts at 5 seconds with jitter. A policy that gives up on channels and consumers at once turns their recovery off, so they need no separate switch.
- D-3 Every close the application did not start triggers recovery, except a full consumer work queue, a protocol or frame error, and the I/O loop stopping on an unhandled exception, which a reconnect would repeat. A reply code does not say whether a failure will last: 403 also means an auth backend is unreachable and 530 a full connection limit, while a deleted vhost or user first arrives as 320. Java recovers on any close not started by the application. .NET does not recover when 403 closes an open connection, but retries forever when a reconnect attempt gets 403. AMQP 1.0 does not recover on security errors.
- D-4 A lost confirmation gets a separate outcome-unknown notification, ordered as I-7 states, and sequence numbers restart at 1. The broker numbers each new channel from 1, and Java, .NET and Go all pass that through. Not waiting for the notification to run means a stuck application callback cannot hold recovery; .NET fails pending confirmations at shutdown and Go nacks them on reopen, neither waiting for the application. The confirm callback keeps the broker's frames, as today. Java abandons these publishes and wakes a waiter with the close reason; AMQP 1.0 reports them as rejected; .NET fails them only with confirmation tracking on; Go resolves deferred confirmations as nacks, which an application cannot tell from a real nack.
- D-5 A channel the broker closes with no call waiting is recovered; one closed in reply to a waiting call is not. A consumer timeout or an acknowledgement of an unknown tag may not recur, and the channel's consumers should not be lost to it. A close that answers a call, such as a passive declare's 404, is that call's result. Go reopens a broker-closed channel at once. Java and .NET keep it closed until the next connection recovery, leaving its consumers stopped until an unrelated failure.
- D-6 A broker-cancelled consumer is re-subscribed only when the broker advertises `accept_consumer_cancel_ok`, after pika's `basic.cancel-ok`. Brokers from 4.3.0 to 4.3.6 cancel a timed-out consumer and keep its tag until the client replies, but do not advertise that they accept the reply, and brokers before 4.3 close the connection on one; re-subscribing with a tag the broker still holds gets 530 and closes the connection. A refused re-subscription closes the channel, so it goes through channel recovery, keeping the guarantees for the channel's other consumers and pending confirms. Re-subscribing at once keeps consumers running through a consumer timeout on 4.3 and later, which arrives as a cancel rather than a channel close, for the same reason D-5 recovers a broker-closed channel. Automatic re-subscription therefore needs RabbitMQ 4.3.7 or later. Java and .NET reply to the cancel on the same capability on their main branches, unreleased as of October 2026, and Go from v1.16.0. None re-subscribes at once: Java and .NET do so at the next connection recovery, and Go forgets the consumer.
- D-7 After connection recovery each channel reports `OPEN`, then the connection, only once replay has finished. `OPEN` means usable (I-10), and a listener on the connection's `OPEN` can use its channels. Java and .NET expose each channel part way through recovery (Java installs the new channel before restoring its settings), and AMQP 1.0 reopens each publisher and consumer on its own; pika diverges because a channel exposed before its prefetch and confirm mode are restored accepts calls that behave differently from before the drop.
- D-8 Everything recorded is replayed, with an on/off switch and a filter judged per entity. With the switch off, consumers are not re-subscribed, as in Java. A step that fails for good is skipped and reported, and replay continues. Redeclaring a durable queue costs one round trip and restores one deleted while the client was away. Java, .NET and Go replay durable queues too, and Java and .NET have the same per-entity filter. AMQP 1.0 replays only exclusive and auto-delete queues. Java logs a failed entity and continues. Go passes each failure to its optional `OnTopologyEntityError` hook, reports skipped entities on the transition to open after connection recovery, and only logs them after channel recovery.
- D-9 The first connection attempt is not retried. Nothing has been recorded yet, and every reference client leaves this to the application.
- D-10 One recovery driver per connection runs every recovery, one at a time, off the I/O loop, starting after the old generation's loop has stopped; each new connection gets its own I/O thread. Replay then uses the ordinary blocking channel calls, and application code in recovery may block without stalling I/O. Java runs all its recovery on one thread: the old connection's reader thread once its loop ends, or a new thread under Netty. .NET recovers on a thread-pool task, Go on a watcher goroutine, AMQP 1.0 on an executor. Java fixed two deadlocks caused by recovering on an I/O thread (rabbitmq/rabbitmq-java-client#413 and #1708).
- D-11 Calls during recovery fail fast. A call that waits silently, or succeeds into a half-restored connection, hides the outage. Java fails on the closed delegate, and AMQP 1.0 raises an error naming `RECOVERING`. Go returns the same `ErrClosed` as for a permanent close, and documents a reconnect window in which calls are not refused and can interleave with the channel handshake.
- D-12 Each connection and channel holds its own state, from the five the AMQP 1.0 client uses. A channel can then recover without its connection doing so (D-5).
- D-13 Delivery tags are offset per channel, including `basic_get` deliveries, and stale acknowledgements are dropped. This is .NET's mechanism. Java offsets consumer deliveries but not `basic_get`, so an acknowledgement of a `basic_get` tag after recovery can be dropped or applied to the wrong delivery. Go has no offset.
- D-14 A call waiting for the broker when the connection drops raises the close reason and is not retried. The broker may have acted on it, and only the application knows whether repeating it is safe. Java, .NET and Go all fail the waiting call.
- D-15 Only what the broker accepted is recorded. That keeps channel recovery from replaying the declaration that closed the channel. Java, .NET and Go record a declaration after its reply, and their `nowait` variants after sending; Go records a consumer before `basic.consume` and removes it if the call fails.
- D-16 Faults are injected with toxiproxy and with the broker's own tools. Toxiproxy can stall a socket silently, refuse connections and reset mid-stream, which a test-local TCP forwarder cannot. .NET runs toxiproxy in CI on Linux and Windows; Java uses `rabbitmqctl close_connection` and `stop_app`/`start_app`.
- D-17 A consumer is re-subscribed with its recorded tag, including a broker-generated one, so the application's tag stays valid. Java passes the recorded tag and re-keys its record if the broker returns a different one.
- D-18 `basic_consume` with a tag already active on the channel raises before anything is sent, and recovery skips re-subscribing a recorded consumer whose tag the application has already registered on the channel. A reused tag closes the broker connection with 530. Java does both.
- D-19 Transaction mode is restored. Uncommitted work is lost, and a commit waiting at the drop raises the close reason. Java re-applies `tx.select`.
- D-20 A connection blocked when it dropped reports unblocked when recovery succeeds. The new connection starts unblocked, and an application waiting for the unblocked notification would otherwise wait forever.
- D-21 Detecting a silent network failure needs heartbeats, and the documentation says so. Heartbeats are on by default, because pika accepts the broker's proposed interval. Without them, and without TCP keepalive, which pika enables only when `tcp_options` sets a keepalive option, TCP notices a lost network only while unacknowledged data is outstanding, so an idle connection goes unnoticed until the application next sends.
- D-22 The no-silent-loss guarantee covers confirm mode only. Without confirms the protocol gives the client no outcome to report.
- D-23 A channel the broker closes during replay is recovered inside the replay, so nothing reports `OPEN` while one channel is still `RECOVERING` (D-7). Go reopens a channel closed during replay in place.
- D-24 A replay step refused because the old connection still holds a resource is retried through the delay policy. After an abrupt loss the broker may not yet know the old connection is gone, so an exclusive queue, or an exclusive consumer on a classic queue, is briefly still its; skipping the step would lose those consumers in the ordinary case of a network drop. AMQP 1.0 retries a resource-locked exclusive queue with its backoff policy, recognising it by the error text. pika diverges from Java and .NET, which log and skip it.
- D-25 A connection can be given a list of hosts, and each attempt, the first included, tries them in a newly shuffled order. One unreachable broker node then does not stop recovery, and shuffling spreads reconnecting clients across the nodes. Java tries every address in a shuffled order on each attempt.
- D-26 A server-named queue's new name is reported through a connection notification carrying the old and new names, fired once the record has been updated and before consumers are re-subscribed. An application that keeps the name, to publish to or bind it elsewhere, needs to learn it. .NET does this with `QueueNameChangedAfterRecoveryAsync`; Java's queue-recovery listener is documented as not public API.
- D-28 In confirm mode, a publish accepted by `basic_publish` but not yet written when the channel is lost is reported as outcome unknown. Dropping it silently would lose the message without the application knowing, and the application cannot tell it apart from a publish written but unconfirmed.
- D-29 `basic_ack` or `basic_nack` with `multiple` set and a delivery tag of 0, which the protocol defines as every outstanding delivery on the channel, is sent unchanged after a recovery rather than treated as stale. An application's acknowledge-all keeps working, and on a recovered channel it can only cover the current generation's deliveries. Java special-cases tag 0 the same way in `RecoveryAwareChannelN`.
- D-30 The recovering errors subclass the existing connection and channel wrong-state errors. They stay under the AMQP error bases applications already catch, and they say what happened: the call came at the wrong time.
- D-31 A delay policy that raises gives up, with its exception as the reason. A broken policy is then visible as a `CLOSED` connection or channel, rather than hidden behind a default delay.
- D-32 When a consumer's tag changes during recovery, the application is told the old and new tag through a connection notification. .NET does this with `ConsumerTagChangeAfterRecoveryAsync`.
- D-33 Just before a recorded consumer is re-subscribed, the application may change its arguments. .NET allows this with `RecoveringConsumerAsync` and documents it for moving a stream consumer's offset.
- D-34 A channel's attempt count resets only once the channel has stayed `OPEN` for a while after recovering; a failure before then counts as another attempt and waits for the policy. Without this, a failure that recurs right after each reopen, such as an acknowledgement of an unknown tag or a consumer timeout on every message, would cycle without limit or delay. Go has that gap, counting each reopen from zero.
- D-35 Deliveries queued for a consumer's callback when the connection drops are still dispatched, and their acknowledgements are dropped as stale (D-13). For `auto_ack` deliveries the queue holds the only copy. Java's consumer work service keeps draining work already queued; .NET disposes the replaced channel and drops its handlers.
- D-36 A consumer that is given up leaves the record, and so does a queue whose re-subscription got a 404. The broker has said they are gone, so the next connection recovery does not recreate them.
- D-37 Registering callbacks and listeners is accepted while `RECOVERING`, so an application can react to recovery while it is under way.

## Designs already rejected

Each is the obvious design from a standing start, so it is recorded to keep it from being proposed again.

- R-1 Recovery state kept apart from the connection's state. No public call consults it, so an application cannot ask whether recovery is under way and has nothing to catch. `findings.md` shows the reference clients fail fast instead.
- R-2 Recovery on an I/O loop that outlives each socket. Replay could not use the blocking channel calls, which wait for replies only that loop can read, so every declaration would need rewriting as chained callbacks; the delay policy, filter and listeners could never block; and it depends on the I/O loop surviving a socket's death, which pika has never done. D-10 is used instead.
- R-3 A broker-closed channel is final. A consumer timeout would then cost the channel's consumers, and the application would have to rebuild what the record already holds. D-5 recovers it instead, and D-34 bounds a failure that recurs.
- R-4 Not recovering on 403 or 530. Both include transient failures, so stopping on them gives up in the cases recovery exists for. D-3 leaves that to the delay policy.
- R-5 Topology recovery modes: all, only transient entities, or none, as Go has. The filter expresses all three, and "only transient" assumes durable entities survive, which an out-of-band delete breaks.
- R-6 Confirm sequence numbers that keep increasing across recovery. It diverges from all three 0.9.1 clients and would mean rewriting the broker's frames before the confirm callback sees them. As in those clients, an application that tracks pending publishes clears them when the channel is lost (D-4).
