# The thread-safe connection

The long-form record for `pika/adapters/thread_safe_connection.py`, which provides `pika.Connection` and its `Channel`. The published docs describe the contract; this is the behaviour behind it and the measurements that pinned it down.

## How it works

`Connection` wraps `SelectConnection` and runs its IOLoop on a dedicated background thread. Every channel operation from an external thread is routed through `add_callback_threadsafe`, so `_tx_buffers` has a single owner and socket I/O stays on one thread. `Channel` exposes a blocking API over that, built on `_blocking_rpc`, which schedules the call on the IOLoop thread and waits for the broker's response.

Deliveries and publisher confirms are dispatched on a per-channel worker thread from `_BoundedWorkPool` rather than on the IOLoop thread. One worker per channel means deliveries on a channel are processed serially, so prefetch controls how many messages are outstanding rather than how many threads run. See the first invariant below for which callbacks go where.

## Invariants

**Which thread a user callback runs on depends on the callback.** Delivery, publisher-confirm, return and cancel callbacks go to the channel's worker pool. `Connection.Blocked` and `Unblocked` go to a separate connection-level pool. Four run on the IOLoop thread: `basic_publish`'s `on_publish`, `on_close_callback` and `on_open_error_callback`, and anything passed to `add_callback_threadsafe`.

**Only the pool-dispatched callbacks and `on_publish` are exception-safe.** `_safe_dispatch` wraps those, logging a failure instead of letting it reach the IOLoop. The other three IOLoop-thread paths are unwrapped, so an exception there exits the IOLoop thread. `_run_ioloop` catches it, records `_closed_reason`, wakes every blocked caller and shuts the pools down, and `is_open` and `is_closed` then report the connection as finished rather than open (#1743). `_safe_dispatch` catches `Exception` rather than `BaseException`, so `_BoundedWorkPool._run_worker` carries its own `BaseException` guard behind it. That makes containment a property of the pool instead of a pairing its callers have to remember, and it covers the gap `_safe_dispatch` leaves.

**What a lost worker used to cost, measured, because it is not what it looks like.** The queue behind a dead worker is orphaned but not silent: the next `work_queue_maxsize` submits succeed and are lost, and the one after that blocks for `work_queue_put_timeout` and raises `WorkQueueFullError`, which `_submit_or_terminate` routes to `_terminate_stream`. So the connection did eventually close with an error the application could catch by type, after discarding 1000 deliveries on the default settings and taking 30 seconds to say so, under a reason indistinguishable from a genuinely slow consumer. Guarding the worker removes that signal along with the data loss. Whether a callback raising outside `Exception` should instead close the channel, the way the Java client's default `StrictExceptionHandler` does, is #1754.

The guard catches `BaseException` rather than `Exception` because the cases that distinction admits have no meaning on a worker thread worth preserving. `SystemExit` raised off the main thread ends only that thread, leaving the interpreter running, and Python prints nothing for it. The mechanism differs by version, so do not grep for one and conclude the other is unaffected: 3.8 and later return early from `threading.excepthook`, while on the 3.7 floor `threading.excepthook` does not exist and `Thread._bootstrap_inner` carries its own `except SystemExit`. That difference is observable, because a `try/except` catches subclasses and an identity check does not. Measured, stderr bytes from a worker thread raising each:

| raised | 3.7.17 | 3.14.5 |
|---|---|---|
| `SystemExit` | 0 | 0 |
| a subclass of `SystemExit` | 0 | 809 |
| `KeyboardInterrupt` | 628 | 831 | `KeyboardInterrupt` cannot arrive here from a signal, since CPython delivers SIGINT to the main thread, so it appears only when user code raises it.

Two members of `BaseException` are ordinary per-item failures rather than requests to stop, and the guard treats them as such: `asyncio.CancelledError`, which a callback awaiting a cancelled future raises and which stopped subclassing `Exception` in 3.8, and gevent's `GreenletExit`, which subclasses `BaseException` precisely so `except Exception` cannot absorb it. Logging and continuing is right for both.

**A recorded close reason means the connection is finished.** `_closed_reason` is written at three sites, all terminal: the broker close, the forced close when the IOLoop will not stop, and the crash above. The four `is_open` and `is_closed` properties rely on that, and `Channel` keeps its own state as well, so a channel closed on its own reports closed while its connection reports open.

**No worker thread is free of back-pressure.** Every pool is a `_BoundedWorkPool`, the per-channel ones and the connection-level one for `Connection.Blocked` and `Unblocked` alike, each constructed with the same `work_queue_maxsize` and `work_queue_put_timeout`. A pool's queue holds `work_queue_maxsize` pending dispatches, 1000 by default. When a slow callback fills it, the IOLoop thread blocks while enqueuing the next item, sends no heartbeats for the duration, and raises `WorkQueueFullError` if the queue stays full for `work_queue_put_timeout` seconds. So "a worker thread means slow callbacks cannot stall heartbeats" is true only while the callback keeps pace. Published prose that states it absolutely is wrong.

**A pool worker must never join the IOLoop thread, and the window where that could happen is narrow.** `close()` detects it is running on one of the connection's own pool workers and returns without joining, because the IOLoop thread's cleanup tail joins that same worker: #1686. The window is inside `Channel._shutdown_pool`, which calls `_claim_pool_shutdown()` to prune the channel from `_channels` and only then joins the worker, so between those two statements the channel is absent from the list while the IOLoop thread is blocked on that worker. Under `close(timeout=None)` the tail's own `_shutdown_pool()` also passes `None`, so the deadlock is permanent.

Searching `_channels` for the answer was tried and defeated by that window: the predicate answered False mid-prune and `close()` fell through to `_ioloop_thread.join`. The other pruning path, `_on_broker_close`, is not the hazard, and must not be mistaken for it: `_shutdown_all_consumer_pools` snapshots `_channels` after that removal, so the tail never joins a worker whose channel the broker closed. Each pool therefore stamps its owner on the worker thread it starts, held weakly at both ends: a thread is a garbage-collection root while it runs, so a strong edge would let a worker still inside a callback pin the connection, its socket and every recorded traceback.

That asymmetry also means an acceptance test cannot pin the predicate. On the `_on_broker_close` path the misclassification is harmless, for the reason above, so a broker-closed channel returns promptly from `close()` under either predicate. `ConnectionTests.test_is_pool_worker_thread_survives_its_channel_being_dropped` is what fails if the `_channels` search comes back.

**What `close()` from a pool worker forfeits.** It returns having only scheduled the close, so it skips the bounded `_ioloop_thread` join, the force-stop, the recorded close reason and the wake-up of blocked callers. On a healthy broker none of that matters, because `_on_connection_closed` does all of it when the close completes. On an unresponsive broker nothing on this path has a deadline, so `_closed_reason` stays `None` and blocked callers wait; recovery then depends on the heartbeat checker, and there is none when `heartbeat=0`. That is #1706, and #1748 is the fix.

**Confirm listeners share that single worker and queue with deliveries.** A confirm handler doing synchronous network I/O per ack is therefore subject to the same stall.

## Closing drains the pools before the connection goes away

**The order is cancel, drain, close, and each step depends on the one before it.** `Channel._quiesce` cancels every consumer and waits for each `Basic.CancelOk`, then runs the queued callbacks through `_BoundedWorkPool.drain`, and only then is the channel or connection closed. The cancel is what makes the drain finite: it gives a point after which the broker dispatches nothing more, so the drain has an end to reach.

**The cancel does not mean no further delivery arrives, and assuming it does is how this gets read wrong.** `pika/channel.py` quotes the specification on the point: the client may receive an arbitrary number of messages between sending the cancel and receiving `Basic.CancelOk`. A review instrumented the discard path and found most of a 2000-message stream arriving after the cancel was sent. What the reply bounds is the broker's dispatching, not the client's receiving, and the drain is what covers the difference.

**That window used to destroy those deliveries, which is #1389.** `Channel._on_deliver` discarded anything whose tag was in `_cancelled`: rejected and requeued under manual acknowledgement, and dropped with no callback at all under `auto_ack`, where the broker has no copy left to redeliver. Since `Channel.close` cancels every consumer, every adapter reached it. Measured on `main` with 2000 `auto_ack` messages of 50 bytes, a 10 ms callback, `work_queue_maxsize=50` and `close(timeout=30)`: 1543, 1558 and 1564 lost across three runs, and none after. Every count in this area depends on `work_queue_maxsize`, the body size and the callback's cost, because together they decide how much of the backlog sits at the broker rather than in the client, so quote the configuration with the number or it will not reproduce: at the default queue size the same experiment loses 644 to 786 on `main`. A delivery in the window is now dispatched, as the Java client does -- `ChannelN.basicCancel` removes the consumer only when `CancelOk` arrives, and `processDelivery` refuses to drop a delivery it has no consumer for because the message needs acknowledging. Same measurement after: 2000 of 2000.

**Draining after the close instead silently repeats work.** The acknowledgement never reaches the broker, so it is not refused by it; it fails on the way out. Measured on `Channel.close` with 20 callbacks queued and 40 published: all 40 ran, 19 acknowledgements reached the broker, and it held the other 21 ready for redelivery. The two paths fail differently, which is worth knowing when reading a report. On `Channel.close` the connection is still open, so `basic_ack` schedules normally and the underlying call raises on a closed channel, which the wrapper turns into a log line; the caller sees success. On `Connection.close` the connection is gone, so `basic_ack` raises `ConnectionClosedByClient` at the caller's own call site inside the callback, and `_safe_dispatch` logs it only if the application does not handle it. This is what #1763 fixed.

**Discarding the backlog instead was tried and is wrong, in two independent ways.** For an `auto_ack` delivery the broker drops its copy the moment it writes the frame, and for a message returned as unroutable the broker never stored one, so in both cases the in-process queue holds the only copy: dropping 20 queued items lost 20 messages, measured both ways. Separately, the Java client does not discard either, though it looks as though it does. `ConsumerDispatcher.handleShutdownSignal` queues its shutdown runnable onto the same per-channel queue, which is FIFO, so it runs behind the backlog; `ChannelManager.scheduleShutdownProcessing` awaits that latch under `shutdownTimeout`, 10 s by default, and calls `WorkPool.unregisterAllKeys` only afterwards. The clear removes what survives the timeout, not the backlog.

**`drain` leaves the pool open where `shutdown` does not, and a close depends on that difference.** A shut-down pool rejects at `submit`, and a rejected item is a lost one, so a confirm or a return arriving between the drain and the close would be destroyed by the very call meant to protect it. The close shuts the pool down afterwards, which is what covers that window. `drain` also bounds its own enqueue by the caller's budget rather than by `put_timeout`, since a full queue would otherwise stretch a close 30 s past the timeout it was given.

**A pool worker closing its own connection skips the quiesce entirely.** `Connection.close` tests `_is_pool_worker_thread()` before calling `_quiesce_all_pools` and skips it, so the skip covers every channel and the connection pool rather than just the caller's own; the early return for that thread comes later, after the close has been scheduled. `drain`'s own refusal to wait for a marker queued behind the calling callback is a second guard, and the one that applies on the `Channel.close` path. Those pools still reach the post-teardown drain, so #1763's guarantee does not extend to a close issued from inside a callback.

**A closing channel discards what the broker is still dispatching, so the guarantee is the wrapper's, not the channel's.** `Channel._on_deliver` returns early once the channel is not open: a callback could not acknowledge the delivery anyway, and the `ChannelWrongStateError` from trying would escape into frame processing and abort the transport, which is what a routine close did on `SelectConnection` before this guard. The Java client discards at the same point, in `ChannelN.processAsync` while quiescing. `pika.Connection` and `BlockingChannel` are unaffected because both cancel their consumers and wait for `Basic.CancelOk` before anything is set to CLOSING, so no delivery arrives in that state; a bare `channel.close()` on the other adapters has no such phase and loses what was in flight. Measured on `SelectConnection` closing a channel part way through 400 `auto_ack` messages of 8 KiB: 245 lost on `main`, 195 here. Giving `Channel.close` its own cancel-and-wait phase would close the gap at the channel, and was rejected: it means chaining the `Channel.Close` onto the last `CancelOk`, which changes close timing for every adapter and every caller. 2.0 does not need it either way, since removing the other adapters leaves `Connection`'s wrapper as the only close path. `Channel.close`'s docstring, `docs/modules/channel.md` and the `Discarded %i deliveries` warning in `_transition_to_closed` are what tell a 1.5.0 user, each stating it once.

**A finite `timeout` smaller than the backlog loses `auto_ack` messages, and that is the contract rather than a defect.** The caller asked for the close to be bounded, and bounding it means abandoning work that does not fit. Measured at `work_queue_maxsize=50` with a 50 ms callback and 400 messages of 8 KiB, `Channel.close(timeout=10)`: 339 lost before this change, 181 after, 0 at `timeout=None`. Reducing the 181 further means either exceeding the budget the caller set or shutting the pool earlier, and shutting it earlier is what discards deliveries at `submit`. So the remaining loss is not worth chasing; what is worth keeping is that `timeout=None` loses none and that the published page says which setting guarantees that.

**The Java client does not drain before closing, and this diverges from it on purpose.** `AMQConnection.close` marks the connection shut down, sends `Connection.Close`, waits for `CloseOk`, and only on that reply enqueues each `ConsumerDispatcher`'s shutdown runnable and hands the latches to a separate monitor thread; `close()` then returns and the `finally` closes the socket. So Java's backlog runs after the connection is gone, and a `basicAck` from one of those callbacks reaches `transmit` -> `ensureIsOpen` and throws `AlreadyClosedException` (`AMQChannel.java:477`). Java has the defect #1763 describes. What is taken from Java is everything else: deliveries are dispatched rather than rejected or discarded, nothing is nacked on cancel, the drain is ordered behind the backlog by FIFO, and it is bounded with the remainder abandoned. Treating Java as the authority on the ordering as well would reintroduce the duplicated work, so the justification here is the measurement above, not the precedent.

**The waits this change added are bounded twice: by the caller's deadline and by whether their subject can still answer.** `shutdown` checks `thread.is_alive()`, `drain` rechecks it around both its enqueue and its wait, and the cancel phase gives up once the IOLoop thread has died or the connection has closed, since the replies it waits for come from there. `Channel.close`'s own wait for `Channel.CloseOk` is not: an IOLoop thread killed by a `BaseException` leaves `_closed_reason` unset, and `close(timeout=None)` then waits forever. That predates this change and `main` hangs identically, but it is the one wait here without a liveness condition. Bounding by the clock alone produced two hangs; bounding by a *small fixed* clock value produced message loss, which is worse. A 10 s cap per cancellation looked reasonable and lost 256 to 270 of 2000 `auto_ack` messages, at `work_queue_maxsize=50` with 50-byte bodies and a 10 ms callback: with the work queue full the IOLoop blocks in `submit` for up to `work_queue_put_timeout`, 30 s by default, so the cap fired on a healthy connection, the cancel was abandoned, and the broker kept dispatching into a pool that was about to close. A 5 s cap on reading the consumers cost 1543 of 2000 in the same queue size at 100-byte bodies and 25 ms, and reserving half the budget for the drain cost 641 there. Caps on the caller's budget are safe; smaller fixed ones are not.

## Why the confirm listener runs on the worker thread

The RabbitMQ Java and .NET clients run their confirm listener inline on the I/O thread. pika's wrapper diverges so that a slow listener does not hold up heartbeats, accepting the back-pressure described above as the cost. The same reasoning puts delivery callbacks there.

Idempotency also diverges from nothing: a second `confirm_delivery` on the same channel returns the cached `Confirm.SelectOk` without sending a frame or resetting the delivery-tag counter, which matches Java and .NET.

## Measurements

Every figure below names its configuration, because none of them reproduces without one. `utils/measure_close_loss.py` reproduces the close figures against a live broker, taking the message count, body size, work-queue size, callback cost, timeout and acknowledgement mode as arguments. It is not wired into CI: a run takes as long as the callbacks it times, and it reports counts rather than a verdict. It discriminates between versions, which is how to tell it is measuring the close and not the harness: at 400 messages of 8 KiB with `--timeout none` it reports 339 of 400 lost on 1.4.x behaviour and none once the close drains first.

**An ack does not mean the message reached a queue.** An unroutable publish sent with `mandatory=True` is answered with Basic.Return and then Basic.Ack. In the broker, `rabbit_channel.erl` runs both for one publish: `process_routing_mandatory(true, [], ...)` sends the return, and `process_routing_confirm(MsgSeqNo, [], ...)` calls `record_confirms` for the same sequence number. Measured against 4.3.4, a mandatory publish to an exchange with no matching binding produced `[('RETURN', 'NO_ROUTE'), ('ACK', 1)]` in that order. Code that treats Basic.Ack as proof of routing therefore has to register `add_on_return_callback` as well.

**`next_publish_seq_no` cannot be read after a publish to learn that publish's tag.** `basic_publish` ends by scheduling the work on the IOLoop thread; the counter advances inside that scheduled function. Measured against 4.3.4 with a single publisher thread, three back-to-back publishes read the counter immediately after each call and got the same value all three times, while `on_publish` reported tags 1, 2 and 3 and the counter settled at 4 a moment later. How many reads are stale varies by run, which is what a race looks like; separate runs gave all three stale and the last two stale. `on_publish` is handed the tag the broker will confirm and is the supported way to learn it. The property's own docstring warns only about concurrent publishers, which understates the hazard.

**RabbitMQ 4.3 and later refuse a queue that is neither durable nor exclusive,** answering 541 and closing the connection rather than the channel. pika still defaults `durable=False`, so every example here passes `durable=True`. `examples/README.md` carries the per-version measurements.

## Known gaps

- `confirm_delivery` accepts a non-callable, because the wrapper hands its own closure to the core channel and the `callable()` guard in `pika/channel.py` never sees the caller's object. Confirms are still enabled and the counter still arms; it is the caller's listener that never runs, failing with a logged `TypeError` once per confirmation: #1742.
- `_BoundedWorkPool._run_worker` dispatches without a guard, so an exception from the submitted function ends the worker and the queue behind it stops draining. Every pika call site wraps the callback in `_safe_dispatch` first, which is why it does not bite, but the containment is a convention at the call sites rather than a property of the pool: #1751.
- Whether the three unwrapped IOLoop-thread paths should be contained the way pool-dispatched callbacks are: #1752.
- Whether the confirm callback should be required at all, and how the API compares with the Java, Go and .NET clients, is under review for 2.0: #1740.
